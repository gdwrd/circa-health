# SR101 ring: what it is and how JRing talks to it

Static analysis only; nothing was sent to the ring. Tags: **[code]** read in JRing 2.0.8 decompiled (class.method),
**[source]** web page, **[observed]** our read-only PC Bluetooth reads, **[guess]**.
`BLS` = `com.sxr.sdk.ble.keepfit.service.BluetoothLeService` (the obfuscated SDK service; method names are jadx's).

## 1. What it is

- **Protocol family:** the "keepfit" BLE SDK by keeprapid / ShenXinRui (`com.sxr.sdk.ble.keepfit`, SDK 3.0.0), the same
  one behind iBraceletPlus, KeepFit and JYouPro [code `BLS.registerCallback`, package names]. The community calls it the
  "Jring / 56ff" family; the Kmart AU "Anko" ring is a member [source https://github.com/servolok84/smart-ring-dashboard `docs/protocol.md`].
- **App:** JRing `com.jaga.ibraceletplus.jyring` 2.0.8 embeds that SDK unchanged [code].
- **Advert:** the manufacturer data is company `0x594A` ("JY") + MAC + `ver u16 LE, cid u16 LE, did u16 LE, bindflag, bindstate`.
  The app shows a ring only if this "JY" block and service UUID `FEF5` are present [code `BLS.a(String,byte[])`, `DupMainActivity.onScanCallback`].
  Ours decodes to **firmware ver 0x008C (140), cid 0x003A, did 0x0061** [observed + code]. The app names it `cid+did+"V"+ver` = `003A0061V140` [code `DupMainActivity.onGetDeviceInfo`].
- **Chip:** Dialog/Renesas DA145xx. `FEF5` is Dialog's service UUID, and JRing updates firmware with Dialog's SUOTA/SPOTA
  characteristics (`SPOTA_MEM_DEV_UUID` 8082caa8…, `SUOTA_VERSION_UUID` 64b4e8b5…) [observed + code `jyring.ota.Statics`, `keepfit.service.ota.f`].
  servolok names the part as the DA14531 [source above]; we did not confirm the exact part. One seller listing names a Realtek RTL8762
  [source https://sakshambhutani.xyz/hacking/2_hacking/]; the SUOTA code makes that unlikely for this ring [guess].
- **Siblings:** JRing-app rings sold as SR08 / SR08 Ultra (Rogbid), Anko (Kmart), "Smart_Ring" [source https://manuals.plus/jring/smart-ring-manual-7, servolok].
  No public page for "SR101" exists [source: web search, none found].
- **Sensors (likely):** PPG (heart rate, SpO2), accelerometer (steps, sleep), battery; no teardown found [source sakshambhutani].
- **Skin temperature:** the SDK and app have it in full: commands `0x37` / `0x38` / `0x39`, values in 0.01 °C as a pair (surface, body) [code `BLS.t(boolean)`, `BLS.d(String)` cases "37"/"38"/"39", `DupMainActivity.onGetTemperatureData`].
  The app turns it on per device from capability bit 10 of the `0x20` reply (`FUNCTION_TEMPERATURE`) [code `DupMainActivity.onGetBandFunction`].
  **Whether the SR101 sets that bit is unknown.** One read of `0x20` answers it (section 5). The servolok Anko unit shows no temperature [source]. [guess] Most likely the SR101 has no temperature sensor.
- **HID:** GAP appearance "keyboard" and PnP vendor 0x05AC are the ring's "short-video remote" (page-turn keys over HID) [observed].
  The app only toggles it: `0x1B` byte 11 `enableShortVideo` [code `BLS.X`].

## 2. Bluetooth layout

| Service / char | Role |
|---|---|
| `000056ff` | Main command service ("HJT ISSC") [code `SampleGattAttributes`] |
| `000033f3` | Write: 20-byte commands [code `BLS.c(byte[])`] |
| `000033f4` | Notify: 20-byte replies and ring-initiated events [code `BLS.y`] |
| `000057ff` / `33f5` / `33f6` | Raw-data channel (AI audio, images, Wi-Fi) for other devices [code]. **Absent on the SR101** [observed] |
| `0000fef5` + SUOTA chars | Dialog firmware update. **Do not write** [code `ota.Statics`] |
| `0000ff12` / `ff15` ("FOTA") / `ff14` | Not referenced anywhere in JRing [code: no match]. [guess] A vendor second OTA path; leave alone |
| `180f` / `2a19` | Battery %, plain GATT read [observed] |
| `2a37` (HR measurement) | Handled if present [code `BLS.a(String,…)`]; not on the SR101 [observed] |

## 3. Framing and handshake

- **Frame:** always 20 bytes. Byte 0 is the command and bytes 1..19 the payload, zero-padded. Integers are little-endian (`utils.c.a(int)`) [code].
  **No length, no checksum, no encryption** [code: every builder in `BLS`]. The replay vector in `BLS.i()` confirms it: the last byte is plain data in every frame.
- **Reply:** the same command byte means success; `cmd | 0x80` means failure (e.g. `81`, `8B`, `90`, `96`) [code `BLS.d(String)`]. Frames shorter than 20 bytes are dropped.
- **Integrity:** only the `0x0C` reply carries a check, CRC-32 (poly EDB88320) over bytes 1..15 with seed `0x4A59AF55`, stored LE in bytes 16..19 [code `BLS.d` case "0C", `utils.e.a(long,long[])`].
- **Timestamps:** the ring's RTC holds local wall-clock epoch seconds. Every ring timestamp equals UTC + the phone's TZ offset; the SDK subtracts `f1` [code `BLS.Y`, `BLS.d`].
- **Write queue:** with-response writes, one at a time. Some sensor commands jump the queue (`a(bArr,true)`) [code `BLS.a(byte[],boolean)`].
- **App-side licence:** the SDK will not scan or connect until `validate_sdk` at `https://openapi.keeprapid.com/developer` returns 200 (cached 24 h, keys in `assets/JySDK.xml`) [code `BLS$…registerCallback`, `scanDevice`, `connectBt`].
  This gate lives in the phone app; the ring never sees it. The app also has a login module (`jyring.sign.LoginActivity`); whether login is mandatory was not checked.
- **Connect sequence (app):** `48`+app-id ×2 → `1D` hour format → `02` user → `1A` goal → … → `01` time → `48` → `10 <day>` history chain [code `DupMainActivity.initParam`, sync block near `getDataByDay(1, iMax)`].
- **Bind (ring-initiated `4B`):** the ring sends `4B 00 00` (not bound) and the app answers `4B 01 00 01`. The ring then sends `4B 02 …` and the app answers `4B 04 00 01` (bonded).
  `4B 06` = unbind ack, `4B 03` = disconnect [code `DupMainActivity.onNotifyBindedInfo`, `BLS.a(int,int,int)`]. Unbind = `4B 05 00 01` [code `FragmentSetting`].
- **`3A` from the ring:** the SDK echoes `3A` and re-sends `48`+app-id [code `BLS.d` case "3a", `BLS.T`].
  servolok sends `3A` every 10 s as a keepalive because the ring drops idle links after ~20 s [source].
- **Legacy:** an `A3 11 <ts BE>` sync with a byte-sum checksum exists but is never started (`BLS.w(true)` has no caller) [code `BLS$n.run`].

Write = to `33f3`; reply = notify on `33f4`. `ts` = u32 LE local-wall-clock seconds at bytes 1..4 unless stated. `day` = days ago, 0 = today (the app syncs up to 6) [code `DupMainActivity` sync, `iMax ≤ 6`].

Sync chain the app runs per day: `10` → `16` → [`39` if temperature] → [`40` if SpO2 history] → [`55` if pressure] → `25`.
It starts the next day after the `25` reply [code `FragmentMain` `…SYNC_DATA_BY_DAY_END`, `DupMainActivity.onGetMultipleSportData`].
Other builders (dials `34/35/36/41/42`, contacts `46`, e-card `4C`, SMS `4D`, ChatGPT `4F`, EQ `53`, Wi-Fi `54`, AI `78`, ECG `2A/2C`, female `44`, rename `30`, reminder `31/32`, BP calibration `33`) target watches and are irrelevant here [code].

## 5. Safe to try from the PC

Write each frame to `33f3` with notify on `33f4`. Every frame is 20 bytes; the hex below shows the non-zero head, then zeros to 20 bytes.
**Checksum: none.** Worked example: the replay frame `03 2D 58 A4 68 92 05 00 00 51 04 00 00 2E 00 00 00 FC 6C 00` ends in `00`, while sum(bytes 0..18) & 0xFF = `0x16` and xor = `0xC6`.
So byte 19 is data, not a check. It decodes to ts 0x68A4582D (2025-08-19 10:55 local), 1426 steps, 1105 m, 46 kcal [code `BLS.i`, `BLS.d` "03"].

Plain reads, in order:

1. GATT read `2a19` → battery % (no write at all).
2. `0B` → `0B pct state`.
3. `0C` → `0C ver mac cid did … crc`; expect ver 0x008C, cid 0x003A, did 0x0061 as in the advert. Check the CRC-32 with seed 0x4A59AF55.
4. `20` → capability bitmap. **Temperature = byte 2 & 0x04; HRV = byte 11 & 0x40; SpO2 history = byte 11 & 0x02; pressure = byte 11 & 0x08.**
5. `03` → `03 ts steps dist kcal …`.
6. `1F` → `1F` + 18-byte device code.

History reads [guess: non-destructive, because they are indexed by day and the app re-reads freely]:

7. `10 00` → `10`/`11` frames for today, then silence.
8. `16 00` → `16 F0…`, `16 A0…`, ends `16 FF`.
9. `39 00` only if bit 10 is set → `39` frames, or `B9`.
10. `40 00` (if bit 81), `55 00` (if bit 83), `25 00` → their frames.
11. Live HR: `14 B4 00 00 00 00` → `14 ts bpm` frames; stop with `15`.

If the ring stays silent, it may want an app id or the bind first [source servolok]. `48 53 6D 61 72 74 52 69 6E 67` ("SmartRing") is a state change: it overwrites the stored app id and may make JRing re-pair. Answering a ring-sent `4B 00 00` with `4B 01 00 01` binds the ring to us. Do either one only on purpose.

**Never send:**

- `0E` with any key: `0E 12 34 56 78 FE DC BA 98` = OTA mode, `0E FE DC BA 98 76 54 32 10` = **device off**, `0E 12 34 56 78 9A BC DE F0` = **restart**, `0E 12 34 12 34 12 34 12 34` = **factory reset** [code `BLS.m(int)`; UI strings "Device off", "Restart device", "Reset device", `SettingMoreActivity`, `FragmentSetting`].
- `4B 05 00 01` (unbind) [code `FragmentSetting`].
- `50 xx` (factory test) [code `BLS.v`].
- `1E …` (overwrite device code), `30 …` (rename), `35/36/41` (dial/wallpaper writes).
- `A3 …` (legacy sync).
- Anything to `fef5` SUOTA characteristics or `ff15` (OTA).

## 6. Could Circa support it

| Data | SR101 (this protocol) | Colmi R02 today |
|---|---|---|
| Steps | per minute (`10`) | 15 min |
| Sleep | per-minute stage: light / deep / wake, **no REM** (`11`) | stages incl. REM |
| Heart rate | per-minute averages while the auto-HR window runs, cadence set by `19` | 5 min |
| HRV / stress | 15-min history (`55`) **only if** cap bits 83/86 are set; servolok's Anko returns 0 for both [source] | 30 min |
| SpO2 | per minute (`40`) if cap bit 81; otherwise spot only (`23 02` → `24`/`3F`) | hourly |
| Temperature | 5-min pair (`39`) **only if** cap bit 10 is set | none on R02 |
| Battery | `2a19` / `0B` | yes |

A sync would need a second protocol class beside `ColmiProtocol`: 20-byte frames on 56ff, set time (`01`), app id (`48`) plus the bind reply,
the day chain above for days 0..N, local-time correction, and a `3A` keepalive. The metrics map onto the existing `SyncWorker.buildMetrics` pattern.
Missing compared with the Colmi: REM, and HRV/stress unless the SR101's `20` bitmap says otherwise.

## 7. Unknowns and how to resolve each

| Unknown | Resolve by |
|---|---|
| Does the SR101 have temperature / HRV / SpO2 history? | Read `20` (section 5 step 4) |
| Must the ring be bound or claimed before it answers? | Send steps 1–5 cold; if it is silent, capture JRing's first-connect sequence |
| Are history reads destructive (does the ring forget synced days)? | Read `10 00` twice and compare; or HCI snoop JRing doing two syncs |
| Meaning of `0B` byte 2, `03` bytes 17..19, `14` byte 6, `16 AA` header | HCI snoop log of JRing (Android developer options → Bluetooth HCI snoop) |
| Purpose of `ff12`/`ff15` "FOTA" | Not in JRing; leave unknown, never write |
| Exact SoC part | Teardown or SUOTA `SUOTA_VERSION` read (read-only) |

## 9. First reads from the PC (2026-11-18, `emu/testdata/sr101/capture1.txt`)

Sent: `0B`, `0C`, `20`, `03`, each a 20-byte frame to `33f3`; the builders were re-read in `BLS` before sending. All **[observed]**.

- **No bind or app id needed:** the ring answered a cold connection, and on subscribing it sent `20`, `0C`, two `F6` frames, `03`, `13` and `0B` unasked.
- **Battery:** `2a19` = 100, `0B 63 01` = 99 %, state 1 (on the charger).
- **Info:** `0C 8C 00 <mac> 3A 00 61 00 …` = ver 140, cid 0x003A, did 0x0061, as in the advert. Bytes 13..19 differ between two replies, so the tail is not a plain CRC of a fixed frame; unexplained.
- **Capabilities:** `20 62 EC 07 38 09 0A BE BB 02 00 1B 00`. Set: heart (6), **temperature (10)**, SpO2 (29), short-video (63), SpO2 history (81), pressure / stress history (83), sugar (84). Not set: HRV (86).
  A set bit means the firmware claims the feature, not that a real sensor is behind it: "blood sugar" is claimed too, and no ring measures that.
- **Clock:** `03` returned ts `0x66FBFC04` and counting, about 2024-10-01: the clock was never set. Steps, distance and kcal are 0.
- **`F6`:** two unasked frames (`F6 00 00 00 8C 00 61 00`, `F6 <mac>`); not in JRing's parser list as read so far.

## 10. Worn, first minutes (2026-11-18 13:10, `capture2.txt`, `capture3.txt`)

All **[observed]**, ring on the finger for a few minutes.

- **Clock:** `01 <local seconds LE> <tz hours>` is echoed and the next `03` reads 2026-11-18 13:10:16. Set.
- **Temperature:** `37 01` is echoed, and 2 s later one `38 1C 0C 20 0E` = surface 31.00 °C, body 36.16 °C, then `27` (measurement done). One reading per `37 01`, not a stream. Believable for a finger just ringed; one value proves nothing yet.
- **Live heart rate:** `14 B4 00 00 00 00` is echoed, the first value comes 11 s later, then about one a second: 67 to 71 bpm at byte 5, then `27`. `15` stops it.
- **Keepalive:** `3A` every 10 s kept the link up for 130 s; the ring did not echo it.
- **History before any background logging:** `16 00` already held the live session as one `16 A0` frame at 13:10:00 with 12 values (71 bpm); `39 00`, `40 00`, `55 00`, `10 00` and `25 00` each answered one frame with a timestamp and zeros = nothing stored.
- **Auto heart rate:** `19 00 00 17 38 01 05 01` (00:00 to 23:56, on, every 5 min) is echoed. The 23:56 end is a typing slip for 23:59; corrected in the next run.
